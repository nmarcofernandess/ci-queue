O que instalar, e onde cada coisa mora

Três lugares diferentes: código versionado, release executada e estado produzido pelos jobs.

  1. RepositórioFonte, testes, docs e catálogo em Git.
  2. Bundle instaladoCópia versionada do executor, API e UI compilada.
  3. State da máquinaTickets, observações, logs, finalização e cadastros locais.
ResponsávelQuando adotar QueueOpcional / limite
MáquinaRelease CI Queue, Node compatível, CLI/worker, Git para provas Git e dependências reais das receitas.API Python 3 e UI compilada servem ao dashboard. gh e acesso GitHub servem ao ship; LaunchAgents automatizam a fila no macOS.
Projeto consumidorComandos de teste existentes e suas dependências.Para usar Queue: catálogo com identidade e receitas. Ship, progress e workflow remoto são escolhas próprias.
Autor da releaseCheckout CI Queue e dependências de desenvolvimento para compilar/verificar o bundle.O consumidor não precisa instalar Vite/Vitest/TypeScript do executor para abrir a UI compilada.

A CLI aceita pedidos. O worker retira tickets, um por vez; o runner prepara e acompanha o subprocesso. A API lê registros e serve a UI. Vite é ferramenta de desenvolvimento/build; a instalação serve arquivos estáticos, não precisa de um servidor Vite de desenvolvimento.

O bundle contém JavaScript compilado, backend Python de biblioteca padrão, interface e manifest. Não inclui automaticamente os binários Node/Python. O package.json observado declara Node >=20.0.0; confirme requisitos da release e de cada projeto. Docker, banco e browser de testes só são necessários quando a receita os usa. O pacote é privado: não presumir instalação por um pacote npm público.

Escolha um state, não crie outra fila por acidente.

Instalação nova normalmente usa ~/.local/state/ci-queue. O diretório compatível ~/.local/state/local-ci/queue, quando existente, é preservado pelo default. --state e CI_QUEUE_STATE_DIR precisam apontar à mesma fila da API/worker. Leia installation.json; este manual não inspecionou o state do seu Mac.

O teste continua independente. O consumidor executa seus comandos sem instalar CI Queue. Quando adota a fila, o catálogo aponta para esses mesmos comandos; executar npm run check, pytest ou seu script diretamente testa o projeto, mas não cria por si só ticket Queue ou prova reutilizável pelo ship genérico. Dashboard fechado não impede execução direta; dashboard saudável não prova execução.

De um comando a um job observável

O projeto escolhe o trabalho. O executor não conhece nutrição nem inventa o resultado que um teste deveria afirmar.

  1. Script independenteExecuta o test runner e preserva exit code.
  2. Recipe argvNome e argumentos exatos no catálogo.
  3. TicketCongela cwd, HEAD, receita e controles.
  4. Worker / runnerPré-voo, subprocesso e pós-voo.
  1. Saída realExit code e stdout/stderr.
  2. RegistrosLog, sidecar, history e finalização.
  3. APIProjeção segura dos fatos.
  4. UIEtapas, logs, fila e histórico.

Receita é um preset nomeado. ["npm","run","check"] é um vetor de argumentos, não uma shell-string. Não esconda && num único argumento: combine comandos num script do projeto. Enqueue grava o argv efetivo, inclusive extras; o runner executa no cwd registrado e não procura uma função DietFlow pelo nome do preset.

Exit code, runtime e verificações Git determinam o resultado. Linha TSV dizendo passed não substitui teste. Falha, timeout, cancelamento, interrupção e instabilidade Git são estados distintos; o log e failureReason explicam quando disponíveis.

PROJECT="$(pwd)"
STATE="$HOME/.local/state/ci-queue" # substituir pelo state instalado conferido
ci-queue config --cwd "$PROJECT" --config "$PROJECT/ci-queue.json" --json
ci-queue enqueue check --cwd "$PROJECT" --config "$PROJECT/ci-queue.json" \
  --state "$STATE" --json
ci-queue status --state "$STATE" --json
# Substituir TICKET_ID pelo id real retornado:
ci-queue logs TICKET_ID --state "$STATE" --json
Não execute um segundo worker.

Na instalação macOS, o LaunchAgent acorda o worker quando há tickets. ci-queue worker é modo manual com state isolado ou ownership comprovado, não o próximo comando automático após enqueue.

--wait espera terminal; encerrar o cliente ou atingir o timeout de espera não cancela o job. Cancelar é explícito: ci-queue cancel TICKET_ID --state "$STATE" --json. Timeout de espera da CLI não é executionTimeoutMs do job.

03 / 11

Progresso que relata, sem fabricar verde

TAB real, IDs estáveis e resultados vindos do processo. O protocolo descreve o trabalho; não o substitui.

Node tem 9 campos; counts tem 12. Separador é TAB real, byte 0x09, não espaços nem os caracteres literais barra-t. O bloco abaixo contém TAB copiável. Os helpers produzem o mesmo byte com join('\t'). Prefixos aceitos: @@ci-queue-progress e legado @@local-ci-progress; versão 1.

@@ci-queue-progress	1	node	static	-	stage	running	-	Static
@@ci-queue-progress	1	node	syntax-src	static	gate	running	-	Sintaxe do módulo
@@ci-queue-progress	1	node	syntax-src	static	gate	passed	12	Sintaxe do módulo
@@ci-queue-progress	1	counts	static	gates	1	2	1	0	0	1	0
LinhaCampos em ordem
nodeprefixo · versão · node · id · parentId ou - · kind · status · duração ms ou - · label
countsprefixo · versão · counts · id já emitido · kind da contagem · completed · total · passed · failed · running · pending · skipped

IDs aceitam letras, números, _ . : -. Mantenha o mesmo ID para atualizar um nó. Use arquivo e título completo para identidade dos casos; evite títulos duplicados. Publique pai antes dos filhos e nó antes de counts. Linha inválida pode ser ignorada; erro de protocolo nunca vira teste aprovado.

Kind de nóExemplo de significado
stageEtapa ampla: Static, Jest, E2E.
groupAgrupamento organizacional abaixo da etapa.
gateVerificação obrigatória do projeto, como typecheck.
suiteArquivo/conjunto do test runner.
caseCaso com nome e resultado reais.
artifactGeração/publicação de arquivo existente; TSV não cria o arquivo.

Estados de nó: pending, running, passed, failed, skipped. Cancelled/interrupted são estados do job, não novos valores de node. Counts aceita gates/suites/cases/artifacts/items e inteiros não negativos:

completed = passed + failed + skipped
total = completed + running + pending
  1. Pai primeiroStatic running.
  2. Filhos reaisSintaxe fonte e sintaxe teste.
  3. Pai concluídoAgregador usa os exit codes.
Pai não é soma dos filhos.

Collector não deduz resultado, duração ou counts pela árvore. Pai pode conter preparação, espera ou paralelismo. Sua duração não é soma de filhos. Nó artifact tampouco publica arquivos: o consumidor declara seu hook terminal e valida seus outputs.

// scripts/progress.cjs: publicação, nunca decide resultado.
const enabled = process.env.LOCAL_CI_PROGRESS_ENABLED === '1' &&
  Boolean(process.env.LOCAL_CI_JOB_ID) || process.env.CI_QUEUE_DEMO_PROGRESS === '1';
const clean = value => String(value).replace(/[\t\r\n]/g, ' ');
exports.node = (id, parent, kind, status, label, duration = '-') => {
  if (!enabled) return;
  process.stdout.write(['@@ci-queue-progress', '1', 'node', id,
    parent || '-', kind, status, duration, clean(label)].join('\t') + '\n');
};
exports.counts = (id, kind, c) => {
  if (!enabled) return;
  const {passed, failed, running, pending, skipped} = c;
  const completed = passed + failed + skipped;
  const total = completed + running + pending;
  process.stdout.write(['@@ci-queue-progress', '1', 'counts', id, kind,
    completed, total, passed, failed, running, pending, skipped].join('\t') + '\n');
};
// scripts/check.cjs: cada comando roda uma vez; primeira falha encerra.
const {spawnSync} = require('node:child_process');
const path = require('node:path');
const p = require('./progress.cjs');
process.chdir(path.resolve(__dirname, '..'));
function run(id, parent, kind, label, argv) {
  p.node(id, parent, kind, 'running', label);
  const r = spawnSync(argv[0], argv.slice(1), {stdio:'inherit', env:process.env});
  const exit = Number.isInteger(r.status) ? r.status : 1;
  if (r.error) console.error(r.error.message);
  if (r.signal) console.error(`Comando encerrado por ${r.signal}`);
  p.node(id, parent, kind, exit === 0 ? 'passed' : 'failed', label);
  return exit;
}
function main() {
  p.node('static', null, 'stage', 'running', 'Static');
  for (const [id, label, file] of [
    ['syntax-src', 'Sintaxe do módulo', 'src/math.cjs'],
    ['syntax-test', 'Sintaxe dos testes', 'test/math.test.cjs'],
  ]) {
    const exit = run(id, 'static', 'gate', label, [process.execPath, '--check', file]);
    if (exit) { p.node('static', null, 'stage', 'failed', 'Static'); return exit; }
  }
  p.node('static', null, 'stage', 'passed', 'Static');
  return run('jest', null, 'stage', 'Jest', [process.execPath,
    'node_modules/jest/bin/jest.js', '--config', 'jest.config.cjs', '--runInBand']);
}
process.exitCode = main();
module.exports = {
  testEnvironment: 'node',

// scripts/jest-results.cjs: resultados REAIS após o Jest terminar.
// Não promete streaming caso a caso. Retorna o resultado intacto.
const {createHash} = require('node:crypto');
const path = require('node:path');
const p = require('./progress.cjs');
const hash = text => createHash('sha1').update(text).digest('hex').slice(0,16);
module.exports = result => {
  for (const suite of result.testResults) {
    const file = path.relative(process.cwd(), suite.testFilePath);
    const sid = 'suite:' + hash(file);
    const suiteState = suite.testExecError || suite.numFailingTests ? 'failed' :
      suite.numPassingTests ? 'passed' : 'skipped';
    p.node(sid, 'jest', 'suite', suiteState, file);
    const c = {passed:0, failed:0, running:0, pending:0, skipped:0};
    for (const test of suite.testResults) {
      const label = [...test.ancestorTitles, test.title].join(' > ');
      const status = test.status === 'passed' ? 'passed' :
        test.status === 'failed' ? 'failed' : 'skipped';
      c[status]++;
      const duration = Number.isSafeInteger(test.duration) && test.duration >= 0
        ? test.duration : '-';
      p.node('case:' + hash(file + '\n' + label), sid, 'case', status, label, duration);
    }
    p.counts(sid, 'cases', c);
  }
  return result;
};

No package.json, "check": "node scripts/check.cjs". São dois syntax checks reais seguidos de uma invocação Jest. Falha propaga código não zero. O processor publica suites e casos após o Jest; o stage Jest é publicado antes pelo wrapper. Suite sem duração conhecida permanece sem duração, não recebe zero inventado. Configuração do processor: referência oficial Jest 30.

Retry, falha e artefato

@@ci-queue-progress	1	node	jest	-	stage	running	-	Jest
@@ci-queue-progress	1	node	suite-api	jest	suite	running	-	API
@@ci-queue-progress	1	node	api-case	suite-api	case	failed	35	Responde a consulta
@@ci-queue-progress	1	node	api-case	suite-api	case	running	-	Responde a consulta
@@ci-queue-progress	1	node	api-case	suite-api	case	passed	41	Responde a consulta

Esse bloco ilustra uma sequência observada, não é script de teste. Failed → running no mesmo ID incrementa retry; novo ID perde a relação e running repetido não é retry. O projeto define a política de flaky e o exit code final. O collector não transforma retry em autorização de verde.

Para outputs necessários: o consumidor congela um hook finalization v2. Após postflight, o hook publica bytes no owner consumidor, retorna referências com hash e diagnóstico de cleanup. Hook é opcional salvo contrato declarado. Publicação válida pode concluir com aviso de limpeza incerta; outputs inválidos, error, recovery pendente e fase failed/interrupted continuam recusados. Não reinterpretar failed histórico. A Queue não copia mídia. Sem consumidor real, não gerar arquivo. Um emissor pode relatar geração com kind=artifact, mas label/TSV não cria arquivo nem URL. Falha de geração deve produzir node failed e saída não zero do script quando ela for obrigatória.

SituaçãoComportamento observado
progress:true + emissorWorker liga env, collector persiste e drawer mostra árvore.
Declarado sem emissãoSem nós: Empty factual. No fim pode haver somente Artefatos; isso não prova instrumentação da receita.
TSV sem declaraçãoCollector pode capturar, mas drawer prioriza aviso de configuração. Emitir não altera a flag capturada no ticket.
Legado sem flagBooleano público false; aviso e resultado preservado. Não reescrever histórico.

Três tempos diferentes

TempoFonte e limite
EmissorDuração explícita não negativa; zero somente quando medido. Prevalece sobre estimativa.
CollectorIntervalo monotônico observado running→terminal do mesmo ciclo. Não soma filhos nem tentativas.
TelaDecorrido do job vivo calculado pelo browser; não é duração de nó, ETA ou percentual.

Missing-start, missing-end, collector-restarted e clock-invalid explicam medidas ausentes. Ausência não é zero. Duração de retry representa a tentativa corrente, não todas somadas.

Quem escolhe o teste que autoriza ship

Uma receita aceita pode provar o pacote. Dois nomes em acceptedPresets não significam duas verificações obrigatórias.

OR, não AND.

acceptedPresets: ["lint","test"] permite uma receita elegível. Para exigir lint e testes, crie check agregador com propagação de falha. O exemplo anterior executa Static e Jest. Aceite somente esse agregado quando ambos forem obrigatórios.

  1. Projeto escolheScripts e política em Git.
  2. Catálogo declaraReceitas alternativas aceitas.
  3. Ship procuraLatest terminal canônico por receita.
  4. Reuso / enqueueSem prova: primeira da lista.

Adotar um terceiro projeto

Git já inicializado, remote/base reais, comando de teste funcional e dependências do projeto presentes. Init não cria Git, teste, dependência ou serviço e não cadastra o projeto na UI. Ele pode inferir scripts.check inequívoco; argv explícito evita adivinhação.

git remote -v
git branch --show-current
git status --short
ci-queue init --cwd "$PWD" --name "Meu projeto" --base-ref origin/dev \
  --argv-json '["node","scripts/check.cjs"]' --json
# Trocar origin/dev pela base real do projeto.
# Init pode declarar progress, mas não escreve o emissor.

Autoria → prova → integração

  1. 1 · AutoriaCatálogo/scripts/docs commitados; branch publicada; PR draft.
  2. 2 · Congelar alvoH, B0, PR, cwd e catálogo em H; árvore limpa.
  3. 3 · ProvaReuso ou enqueue e resultado elegível.
  1. 4 · Ready/remotoAtestar, marcar ready, veredito opcional.
  2. 5 · MergeRevalidar e enviar sha=H.

# Publicação da branch, depois de revisar os arquivos:
git add ci-queue.json scripts/ src/ test/ jest.config.cjs package.json
# Incluir AGENTS e a skill/instrução atualizada.
git commit -m "chore: document and configure local CI"
git push -u origin HEAD
gh pr create --base dev --draft --title "Configurar CI local" \
  --body "Receita real e contrato de integração."
# Inspeção: não cria prova nem mergeia.
ci-queue ship --cwd "$PWD" --config "$PWD/ci-queue.json" \
  --state "$STATE" --dry-run --no-remote --json

Sem prova reutilizável, dry-run genérico retorna LOCAL_RED: esperado, ele não enfileira. Execução real pode enfileirar/esperar antes do merge. O comando seguinte não é simulação e só deve ocorrer com autorização:

ci-queue ship --cwd "$PWD" --config "$PWD/ci-queue.json" \
  --state "$STATE" --no-remote --json

Receita aceita precisa de requireCleanTree=true, requireGitStability=true, pinHeadSha=true e fetchBase não vazio. Ticket precisa ser queue/legado compatível, passed/exit0, argv/flags canônicos, cwd/H/B0 e snapshots limpos/iguais. Genérico também exige projectId. Progress e receipt Node não entram na elegibilidade.

Latest por receita considera somente terminais, ordenados por startedAt (fallback createdAt, desempate id). Failed/cancelled/interrupted posterior impede ressuscitar verde velho da mesma tupla. Queued/running não sombreiam. Genérico reusa a primeira receita cujo latest é elegível; DietFlow escolhe a candidata com finishedAt mais recente. Sem prova, [0] é default.

HEAD pinado, base observada.

PUT de merge recebe sha=H. Revalidar B0 antes e inspecionar depois não é lock atômico H+B. MERGED_BASE_CHANGED pode significar merge já realizado: inspecione antes de repetir.

Política por diff é do projeto. DietFlow usa scripts/ci/classify-pr-paths.mjs para docs-only e recomendação de Full. Genérico não traz classificador clínico nem dispensa automática para README. Não inventar classificador no executor.

Adoção e método portáveis

O owner genérico é TESTING-METHOD; seus templates são copiados para o consumidor. Resolver mapa e method desde a raiz desse repositório, default docs/ci/TESTING-METHOD.md, ou seu owner existente (DietFlow: docs/ci/FEEDBACK-LOOP.md). Feedback permanece indisponível até existir receita real. Adoção standalone não exige ship-bound: ship é opcional, e as flags da prova só governam as receitas aceitas por ele. O consumidor escolhe o executor; Jest puro pode rodar diretamente com a mesma seleção.

Adoção inclui instruções do consumidor

Atualizar AGENTS.md ou seu alvo se symlink e skill/instrução operacional versionada: entrada canônica, comando standalone, fila/state conferido, dono da política, autorização de ship, progress como aviso e diagnóstico. Uma fonte editável com ponteiros, não dez cópias de contrato. Skill externa ao Git exige delta e caminho, sem alegar aplicação local.

Sem crédito não significa sem prova

A política remota muda a espera pelo veredito, não elimina a identidade da entrega.

ControllerArquivo e valoresFlags

{ "verdict": "skipped" }

Skipped continua exigindo prova/PR/identidade/árvore/HEAD/base/permissões. DietFlow conserva sua exceção docs-only. --no-remote não transforma JSON inválido em autorização, não detecta budget e não substitui autorização humana. Nunca usar status manual, ticket fabricado, push em dev ou --admin para contornar falha.

  1. Worker terminaGrava resultado e registros.
  2. Operador invoca shipNa lane e com autorização.

Passed sozinho não dispara ship. Worker nunca mergeia; dashboard não tem botão de merge. O HTML é estático e não chama ações.
